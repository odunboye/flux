# Flux local socket and load results — 2026-09-09

Tested the built example server on Darwin arm64 at source commit db2946ae70f401e4f2c73689bdc68a75b87fb085. No framework implementation changes were made. Raw responses, wrk output and timed resource samples are in the adjacent JSON file.

## Confirmed protocol observations

- Missing Host on HTTP/1.1 returns 200.
- Invalid Content-Length and conflicting Content-Length values each produce an application-level JSON 400 followed by a pipelined 200; the parser did not reject the framing and close the connection.
- Transfer-Encoding: chunked together with Content-Length: 0 likewise produces an application 400 followed by 200. This is a framing ambiguity; no reverse-proxy exploit was attempted.
- A chunked POST without Content-Length produces two 400 responses and closes: the chunk framing is interpreted as another request rather than decoded as a body.
- HEAD / returns 405 with an actual 18-byte body, Method Not Allowed. The issue is the body, independently of whether HEAD routing is supported.
- Connection: close receives 200 but no EOF during the 400 ms observation window.
- An AppError 404 omits CORS/security/request-ID headers that appear on ordinary responses.

## Behaviors exercised successfully

Ordinary GET, two pipelined GETs, fragmented headers, static streamed content, invalid-JSON handling followed by a valid pipelined request, header-size rejection, declared-body-size rejection, and handler body-size rejection. The oversized handler body produced 413 and closed before the next pipelined request. An unfinished header connection closed within the four-second observation window with a configured 1.5-second timeout.

A truncated body returned an application JSON 400 and EOF, but this is not evidence that truncation itself is detected by the framing layer: the supplied partial body was already invalid for the handler.

## Bounded sustained load

wrk used two generator threads, 100 connections, GET /, a two-second client timeout, one shared established session cookie, 128 server workers, and a five-second server idle timeout. Each row used a fresh server. Resource sampling was approximately every two seconds, followed by twelve seconds of recovery.

All servers answered a post-load GET. At the final recovery sample all had only their listening TCP socket and no CLOSE_WAIT connections. RSS remained above its startup baseline; this short run cannot distinguish retained heap capacity from a leak or establish an hours-long bound. The two- and four-thread workloads showed socket errors and severe throughput degradation. Root cause was not established.

## Limits and reproducibility

An independent benchmark/server pair on port 8125 was observed on the shared machine and left untouched. These are diagnostic numbers, not isolated comparative benchmarks. Reusing a single session avoids unbounded session creation by wrk, but intentionally causes contention on one session stripe. The lower-than-default server timeout can contribute to read errors during stalls. Latency percentiles cover wrk's measured responses and do not erase failed requests.

An initial run was discarded for resource analysis because sampling targeted the generated shell launcher. The retained run executes the Chez program directly with the launcher's library environment. All retained server processes were reaped after SIGTERM without requiring SIGKILL; their exit status was -15, so this is not evidence of graceful in-flight draining. The harness is diagnostic and exits zero on completion even when protocol observations violate expectations.

Run `pack --no-prompt build examples/examples.ipkg`, then `python3 test/socket_suite.py`. Requires Python 3, wrk, ps and lsof. It binds only loopback, uses temporary logs, and takes roughly three minutes. The harness currently targets the generated Chez executable layout.
